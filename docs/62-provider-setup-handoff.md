Browser preview callbacks differ and need separate explicit registration.
5. Read issuer and `jwks_uri` from the tenant's OIDC discovery document. Preserve the exact issuer, including a trailing slash where supplied.
6. Prove login, refresh, sign-out/revocation, cancellation, wrong audience and account switching on both native platforms. Staff MFA remains a separate acceptance requirement; creating a tenant does not satisfy it.

## Saved-session environment isolation

Native credential storage now uses a versioned key derived with SHA-256 from the exact API URL, issuer, public client ID, audience, app role and synthetic-mode setting. Moving a build from local/staging to another backend or identity configuration requires signing in for that scope. Matching configurations can restore their own saved session. Sign-out deletes only the current scope; it is not a global logout across environments or the identity provider.

The old role-only `v1` key is never restored or automatically migrated because its original environment cannot be established. Existing development installations must sign in again. Old keychain records are not automatically deleted by this change; they are ignored. Browser previews continue keeping auth tokens only in memory. The hash is a namespacing mechanism, not encryption; native SecureStore provides device-protected persistence as before.

Tests exercise read/write/delete separation across each configuration dimension, matching-scope restore, legacy non-restoration and hash-failure rejection. Actual provider login and physical-device keychain persistence remain required after account configuration.

## Expired sessions without refresh grants

When an access token reaches the client's expiry safety window and no refresh token exists, the credential controller now invalidates pending account work, clears stored credentials and notifies the session UI to return to sign-in. An explicit null renewal result follows the same path. Transient refresh failures still preserve credentials and produce a retryable error; late results still cannot affect a newer session. This matters when offline access is disabled, declined or not issued by the chosen provider.

## Local Auth0 launcher shutdown — September 10

`pnpm dev:api:auth0` now supervises the API in its own process group on POSIX systems. Terminal SIGINT/SIGTERM reaches the launcher first, which forwards it to the API process alone. The API can then drain the worker/pool before stopping embedded PostgreSQL. Repeated signals do not duplicate cleanup; a 15-second deadline terminates the isolated group if cleanup hangs. On Windows the launcher forwards signals to the child without POSIX process-group behavior; that platform has not been verified.

Manual integration checks started the real local API twice, waited for health, then delivered SIGINT and SIGTERM to the launcher's process group. Both exited with code zero, emitted no unhandled pool error and removed the disposable database directory. This resolves the September 9 shutdown issue when using the documented Auth0 launcher. Directly interrupting a manually launched API/PostgreSQL process group still bypasses this protection. The launcher runs without watch mode; restart it after backend edits. The ordinary synthetic preview command is unchanged.
